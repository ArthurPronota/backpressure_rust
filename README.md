# Backpressure в async через bounded-канал

## Что демонстрирует код

Пример показывает **естественный механизм backpressure** в Tokio: производитель (spawn-задача) отправляет 20 чисел в канал, а потребитель (главная задача) читает их с задержкой в 1 секунду. Благодаря **ограниченному буферу** канала (`mpsc::channel(8)`), производитель **вынужден ждать**, когда буфер заполнен, и не может «убежать вперёд» и забить память.

## Разбор кода по частям

### 1. Создание канала

```rust
let (tr, mut rs) = mpsc::channel::<i32>(8);
```

- `mpsc::channel::<i32>(8)` создаёт **multi-producer, single-consumer** канал с буфером на **8 сообщений**.
- Возвращает кортеж: `(Sender<i32>, Receiver<i32>)`.
- `tr` — transmitter (отправитель), `rs` — receiver (получатель).
- `mut rs` — получатель должен быть изменяемым, потому что `recv()` требует `&mut self`.
- **`8` — это граница backpressure.** Как только в буфере окажется 8 непрочитанных сообщений, следующий `send()` будет **ждать**, пока получатель не заберёт хотя бы одно.

### 2. Производитель (spawn-задача)

```rust
tokio::spawn(async move {
    for i in 0..20 {
        println!("Before send: {i}");
        tr.send(i).await.unwrap();
        println!("After send: {i}");
    }
});
```

- `tokio::spawn` запускает задачу в runtime.
- `async move` захватывает `tr` **по значению** (владеет отправителем).
- Цикл от 0 до 19 (20 итераций).
- **`tr.send(i).await`** — ключевой момент:
  - Если в буфере **есть место** — `send` завершается **немедленно**, сообщение кладётся в буфер.
  - Если буфер **заполнен** (8 сообщений) — `send` **приостанавливает задачу**, пока получатель не освободит место.
- `.unwrap()` — паника, если получатель закрыт (в этом примере не происходит).

**Порядок вывода важен:**

```
Before send: 0
After send: 0
Before send: 1
After send: 1
...
```

`Before` печатается **до** отправки, `After` — **после**. Если буфер заполнен, между `Before` и `After` будет **пауза** — задача ждёт.

### 3. Потребитель (главная задача)

```rust
while let Some(v) = rs.recv().await {
    println!("Readed: {v}");
    sleep(Duration::from_secs(1)).await;
}
```

- `while let Some(v) = rs.recv().await` — цикл, пока канал не закрыт.
  - `recv()` возвращает `Some(v)`, если есть сообщение.
  - `None`, если все отправители дропнуты и буфер пуст.
- `println!("Readed: {v}")` — печатает полученное значение.
- **`sleep(Duration::from_secs(1)).await`** — **искусственная задержка**. Это ключевой элемент: потребитель **медленный**, обрабатывает одно сообщение в секунду.

## Что происходит при выполнении

### Фаза 1: буфер заполняется

Производитель быстро отправляет первые 8 сообщений. Они попадают в буфер, потому что там есть место. Вывод:

```
Before send: 0
After send: 0
Before send: 1
After send: 1
...
Before send: 7
After send: 7
```

### Фаза 2: производитель блокируется

На 9-м сообщении буфер **полон** (8 непрочитанных). `tr.send(8).await` **приостанавливается**. Вывод замирает на:

```
Before send: 8
```

### Фаза 3: потребитель начинает читать

Тем временем потребитель просыпается, читает первое сообщение, печатает `Readed: 0`, засыпает на 1 секунду. Это **освобождает место** в буфере. Производитель **просыпается**, кладёт сообщение 8 в буфер, печатает `After send: 8`, идёт дальше.

```
Readed: 0
After send: 8
Before send: 9
```

### Фаза 4: цикл повторяется

Каждую секунду потребитель забирает одно сообщение, освобождая место, а производитель отправляет следующее. В итоге производитель **замедляется** до скорости потребителя — примерно **1 сообщение в секунду**.

### Итоговый вывод (примерный)

```
Before send: 0
After send: 0
Before send: 1
After send: 1
...
Before send: 7
After send: 7
Before send: 8          ← producer ждёт
Readed: 0
After send: 8           ← consumer забрал 0, producer отправил 8
Before send: 9
Readed: 1
After send: 9
Before send: 10
Readed: 2
After send: 10
...
Readed: 19
```

Общее время выполнения: **~20 секунд** (по 1 секунде на сообщение), а не мгновенно — именно из-за backpressure.

## Что такое Backpressure

**Backpressure** — это **давление потребителя на производителя**. Без него быстрый производитель забивает память, потому что потребитель не успевает обрабатывать данные.

### Без backpressure (unbounded-канал)

Если бы канал был **неограниченным**:

```rust
let (tr, mut rs) = mpsc::unbounded_channel::<i32>();
```

Производитель мгновенно отправил бы все 20 сообщений, они все легли бы в память, и только потом потребитель начал бы их читать. Память **росла бы бесконтрольно** — при больших объёмах данных это OOM.

### С backpressure (bounded-канал)

С `mpsc::channel(8)` производитель **физически не может** отправить больше 8 сообщений «вперёд» потребителя. Он **блокируется** на `send().await`, пока получатель не заберёт сообщение. Память **ограничена** размером буфера (8 сообщений).

## Как реализуется backpressure в async

### 1. Bounded-каналы

Самый прямой способ — **ограниченный буфер** канала:

```rust
let (tx, rx) = mpsc::channel::<T>(N);
```

- `N` — максимальное количество сообщений в буфере.
- `send().await` **ждёт**, если буфер полон.
- Это **встроенный** backpressure: производитель не может обогнать потребителя больше, чем на `N` сообщений.

### 2. Семафор (`Semaphore`)

Если у вас нет канала, но есть **параллельные задачи**, backpressure делается через семафор:

```rust
use tokio::sync::Semaphore;
use std::sync::Arc;

let sem = Arc::new(Semaphore::new(10));   // максимум 10 одновременно

for i in 0..100 {
    let permit = sem.clone().acquire_owned().await.unwrap();   // ждём разрешения
    tokio::spawn(async move {
        // делаем работу
        drop(permit);   // освобождаем разрешение
    });
}
```

- Семафор ограничивает **количество одновременно выполняющихся задач**.
- Когда все 10 разрешений заняты, `acquire()` **ждёт** — это backpressure.

### 3. Ограничение параллелизма через `buffer_unordered`

В `futures`:

```rust
use futures::stream::{self, StreamExt};

stream::iter(0..100)
    .map(|i| async move { /* работа */ })
    .buffer_unordered(10)   // максимум 10 одновременно
    .for_each(|_| async {})
    .await;
```

`buffer_unordered(10)` запускает не более 10 futures одновременно. Остальные **ждут** — это backpressure.

## Почему `send().await` — это backpressure

Ключевое отличие `send().await` от `try_send()`:

| Метод | Поведение при полном буфере |
|---|---|
| `send().await` | **Ждёт**, пока появится место → backpressure |
| `try_send()` | **Возвращает ошибку** `TrySendError::Full` → нет backpressure |
| `send()` (sync) | **Блокирует поток** → не для async |
| `unbounded_send()` | **Никогда не ждёт** → нет backpressure |

Именно **`.await` на `send`** создаёт backpressure: задача приостанавливается, runtime может выполнять другие задачи, а производитель **не может** опередить потребителя.

## Ключевые моменты

### 1. Буфер = 8, сообщений = 20

Производитель **не может** отправить 20 сообщений сразу — только 8, потом ждёт. Оставшиеся 12 отправляются по мере освобождения буфера.

### 2. Медленный потребитель = медленный производитель

Из-за `sleep(1s)` потребитель обрабатывает 1 сообщение в секунду. Производитель **вынужден** подстроиться под этот темп. Общее время — ~20 секунд.

### 3. Память ограничена

Максимум в буфере — 8 сообщений. Даже если производитель генерирует миллион сообщений, в памяти будет не более 8 + те, что в обработке.

### 4. `spawn` и `while let` работают конкурентно

- `tokio::spawn` запускает производителя **в фоне**.
- Главная задача выполняет потребителя.
- Runtime **переключается** между ними: когда производитель ждёт на `send`, runtime выполняет потребителя, и наоборот.

### 5. Закрытие канала

Когда цикл производителя завершается (после 20 итераций), `tr` **дропается**. Это закрывает канал. Потребитель, прочитав все сообщения, получает `None` из `recv()` и выходит из `while let`.

## Что было бы при разных размерах буфера

| Размер буфера | Поведение |
|---|---|
| `0` (rendezvous) | Производитель ждёт потребителя **на каждом** сообщении |
| `1` | Производитель ждёт, пока потребитель заберёт предыдущее |
| `8` | Производитель может опередить на 8 сообщений |
| `20` | Производитель отправит все 20 сразу, backpressure не сработает |
| `unbounded` | Backpressure **отсутствует**, память растёт |

## Итог

- **Backpressure** — это давление потребителя на производителя, не дающее производителю обогнать потребителя и забить память.
- В Tokio backpressure реализуется через **bounded-каналы**: `mpsc::channel(N)`.
- **`send().await`** приостанавливает производителя, если буфер полон.
- В примере: буфер 8, сообщений 20, потребитель медленный (1 сек на сообщение) → производитель **замедляется** до скорости потребителя.
- Память **ограничена** размером буфера.
- Альтернативы: `Semaphore`, `buffer_unordered`, `try_send` (без backpressure).
- Без backpressure (unbounded-канал) производитель забил бы память мгновенно.
